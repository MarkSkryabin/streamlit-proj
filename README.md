# Анализ погодных данных и температурных аномалий

**Streamlit-приложение для исследования исторических температур и сравнения текущей погоды с сезонной статистикой.**

Приложение загружает CSV с наблюдениями, строит интерактивные графики, выделяет температурные аномалии и получает текущую погоду через OpenWeatherMap. Дополнительно оно сравнивает время синхронных и асинхронных HTTP-запросов, а также последовательной и многопоточной обработки данных.

## Возможности

- Загрузка исторических температур из CSV.
- Выбор одного из 15 городов.
- Описательная статистика выбранного временного ряда.
- Расчёт скользящего среднего по 30 наблюдениям.
- Средняя температура и стандартное отклонение по сезонам.
- Поиск аномалий за пределами сезонного интервала **μ ± 2σ**.
- Интерактивный временной ряд с выделенными аномалиями.
- Сезонный профиль с диапазонами стандартного отклонения.
- Получение текущей температуры и её сравнение с сезонной статистикой.
- Замеры времени одиночных и серийных запросов к API.
- Сравнение последовательного анализа и `ThreadPoolExecutor`.

## Установка и запуск

### 1. Получите исходники

```bash
git clone https://github.com/MarkSkryabin/streamlit-proj.git
cd streamlit-proj
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Активация в Linux / macOS:

```bash
source .venv/bin/activate
```

Для локального окружения можно использовать Python 3.11. Проверьте установку зависимостей в своей среде.

### 2. Установите зависимости

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### 3. Запустите приложение

```bash
python -m streamlit run app.py
```

Откройте адрес из терминала, обычно [http://localhost:8501](http://localhost:8501).

### 4. Выполните анализ

1. Загрузите CSV с историческими температурами. В репозитории есть файл `temperature_data.csv`, который можно выбрать через интерфейс.
2. Выберите город, присутствующий в загруженных данных.
3. Введите собственный API-ключ OpenWeatherMap в поле с маскировкой ввода.
4. Нажмите **«Начать анализ»**.

Ключ задаётся через интерфейс; `.env` для приложения не нужен. Получить ключ можно в [OpenWeatherMap](https://openweathermap.org/). В текущем интерфейсе запуск исторического анализа также зависит от ввода ключа и успешного запроса текущей погоды.

## Формат входных данных

CSV должен содержать заголовок, разделитель-запятую и четыре обязательных столбца:

| Столбец | Формат и назначение |
| --- | --- |
| `city` | Название города; должно точно совпадать с выбранным в интерфейсе |
| `timestamp` | Дата наблюдения, например `2024-01-01` |
| `temperature` | Числовая температура в °C |
| `season` | `winter`, `spring`, `summer` или `autumn` |

Пример структуры:

```csv
city,timestamp,temperature,season
Moscow,2024-01-01,-8.2,winter
Moscow,2024-01-02,-6.5,winter
Moscow,2024-01-03,-12.0,winter
London,2024-01-01,5.1,winter
London,2024-01-02,6.3,winter
```

Для оценки текущей погоды нужны наблюдения соответствующего сезона. Стандартное отклонение рассчитывается методом pandas `std()`; одного значения в сезонной группе недостаточно для его определения.

Города в интерфейсе:

```text
New York, London, Paris, Tokyo, Moscow, Sydney, Berlin, Beijing,
Rio de Janeiro, Dubai, Los Angeles, Singapore, Mumbai, Cairo, Mexico City
```

Чтобы добавить другой город, измените список `cities` в `app.py` и подготовьте соответствующие данные.

## Метод анализа

### Исторические температуры

Наблюдения выбранного города сортируются по времени. Для каждого сезона по всем доступным годам вычисляются:

- `mean_temp` — средняя температура;
- `std_temp` — выборочное стандартное отклонение;
- `is_anomaly` — признак выхода температуры за границы `mean_temp ± 2 × std_temp`.

Ровно на границе диапазона историческое наблюдение аномалией не считается.

Дополнительно создаётся `temp_ma_30` — скользящее среднее с `window=30`, `min_periods=1`. Окно задаётся количеством строк: 30 дней оно представляет только при ежедневных наблюдениях без пропусков. В текущем интерфейсе эта колонка рассчитывается, но отдельной линией на графике не выводится.

### Текущая погода

Приложение получает температуру через endpoint `/data/2.5/weather` с `units=metric` и проверяет, попадает ли она в сезонный диапазон исторических данных.

Сезон определяется по текущему месяцу на сервере:

| Месяцы | Сезон |
| --- | --- |
| Декабрь — февраль | `winter` |
| Март — май | `spring` |
| Июнь — август | `summer` |
| Сентябрь — ноябрь | `autumn` |

Это правило едино для всех городов и не учитывает смену сезонов в Южном полушарии.

## Эксперименты с производительностью

При нажатии **«Начать анализ»** выполняются:

| Эксперимент | Реализация |
| --- | --- |
| Один синхронный запрос | `requests.get()` |
| Один асинхронный запрос | `httpx.AsyncClient` |
| Серия синхронных запросов | 10 последовательных обращений |
| Серия асинхронных запросов | 10 обращений через `asyncio.gather()` |
| Последовательный анализ | Сезонная агрегация pandas |
| Многопоточный анализ | Обработка сезонных групп через `ThreadPoolExecutor` |

Всего один запуск отправляет **22 запроса к OpenWeatherMap** для одного выбранного города. Это следует учитывать при повторных замерах и использовании квоты API.

Замеры зависят от сети, объёма данных и накладных расходов. Они не гарантируют ускорения: для небольших таблиц многопоточность может оказаться медленнее последовательного расчёта.

Функция `analyze_city_temperature()` использует `st.cache_data`. При повторении тех же входных данных возвращаются и ранее сохранённые времена анализа; это не новый замер вычислений.

## Особенности текущей реализации

- Структура CSV, наличие выбранного города и достаточность сезонных данных отдельно не проверяются. Перед запуском убедитесь, что данные соответствуют описанному формату.
- Исторический `season` берётся из CSV, а не вычисляется из `timestamp`. Проверьте согласованность этих полей.
- При отсутствии данных текущего сезона границы нормы будут неопределёнными; сообщение об аномалии в таком случае не следует интерпретировать как результат полноценной проверки.
- Ошибки соединения и тайм-ауты не обрабатываются на уровне интерфейса. Для асинхронных запросов установлен тайм-аут 2 секунды, для синхронных явный тайм-аут не задан.
- Сезонная норма рассчитывается по загруженному корпусу наблюдений. Её интерпретация зависит от периода и качества данных.
